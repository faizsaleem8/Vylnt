# VYLNT API and deployment setup

Authenticated `POST /api/reports/verify-upload` checks an uploaded raw scan or frozen insights JSON against owner-scoped saved content. Insights verification additionally checks its live anchor using server-owned proof metadata. Uploads are transient, capped at 4 MiB including formatting; no write, import or anchoring occurs. Responses distinguish `matching` (live anchor), `database-matching` (raw scan only), `content-mismatch`, `not-found`, `not-anchored` and `verification-unavailable`. See [report verification](REPORT_VERIFICATION.md).

`GET /demo-api/ledger?before=<inclusive block>` serves the separate `/ledger.html` local presentation without user login. It requires a loopback socket client and the existing origin policy; proxy headers do not grant access. It joins live contract events with deployment-scoped account pseudonyms from the local journal. It never returns journal owner IDs or report evidence. This intentionally presents all known accounts' anchor metadata on this computer; accounts without journal jobs cannot be enumerated. See [demo ledger](BLOCKCHAIN_LEDGER.md).

The authenticated `GET /api/blockchain/ledger?before=<inclusive block>` returns actual contract events in a bounded 200-block range, live checked deployment identity, transaction hashes and block links. No journal owner identifiers or report contents are returned. Results distinguish `live`, `disabled` and `unavailable`; a live event is not a report-content verification. See [demo ledger](BLOCKCHAIN_LEDGER.md) for pagination, visibility and demo steps.

## Local development

Run `npm run setup:local` once, then `npm run build` and `npm run dev`. Open the VYLNT extension side panel and load its workspace connection. The generated local-mode token is in the ignored `.env`; paste it into the panel's connection form. It is not printed to logs. Local mode binds to loopback and uses `.local/scans.json` with serialized atomic writes. Run only one API process against a local data file.

The dashboard and extension keep sessions in page memory only; closing/reloading the page requires reconnecting. Rotate the local token by changing `VYLNT_API_TOKEN` and restarting the server. Local mode has no account registration or password management.

## API contract

All endpoints except `GET /api/health` and `GET /api/config` require `Authorization: Bearer <token>`. The configuration endpoint exposes only the selected mode and Supabase public URL/publishable key. Requests are limited to 512 KiB (524,288 bytes). Errors are JSON with an `error` string; validation failures include field paths without echoing submitted values. HTTP 429 responses include `code: "RATE_LIMITED"` and `Retry-After` seconds.

| Method | Path | Behavior |
| --- | --- | --- |
| POST | `/api/scans` | Accept `{scanId, observation}` only; validate/sanitize, recalculate findings/score, finalize report |
| GET | `/api/scans?page=1&limit=30` | Paginated summaries, total, page and limit (max 100/page) |
| GET | `/api/scans/:id` | Full stored report, SHA-256, received time and feedback |
| GET | `/api/scans/:id/comparisons?page=1&limit=10` | Other owned scans of the exact same sanitized page URL; paginated summaries and total |
| GET | `/api/reports/:id/pdf` | Owner-authenticated PDF attachment of the saved report and saved review notes |
| POST | `/api/reports/:id/insights/pdf` | Separate PDF of grouped recommendations and verified experimental React model results; `{modelHash, values}` |
| GET | `/api/sites?page=1&limit=30` | Paginated origins, full per-site scan counts, latest summaries and global overview metrics |
| POST | `/api/scans/:id/findings/:findingId/feedback` | `{verdict, notes}`; URL-encode the finding ID |
| DELETE | `/api/scans/:id` | Delete owned report and feedback |
| GET | `/api/reports/:id` | JSON report attachment |
| GET | `/api/reports/:id/verify` | Check stored report against saved hash; `anchored: false` |

Scan IDs are UUIDs. Uploading the same normalized snapshot twice returns HTTP 200 on retry; first creation returns 201. A different snapshot with the same ID returns 409. Rescan to produce a new ID. Client-supplied owner IDs, derived findings, scores, and raw cookie values are rejected. Notes are bounded to 1,000 characters; do not put secrets in them.

### Submission and generated-report size limits

The API checks both the request body and the report generated by the shared rules. Findings/recommendations can make a report larger than its submitted observations. Both local and Supabase storage now enforce a 512 KiB generated-report limit before writing or calling ingestion. The shared byte calculation matches PostgreSQL `octet_length(report::jsonb::text)`, including UTF-8 characters and structural spaces. Exactly 524,288 bytes is accepted; one byte over is rejected. Review notes are separate from the immutable report and excluded from this calculation.

Size errors return HTTP 413 with `limitBytes: 524288` and `code: "SUBMISSION_TOO_LARGE"` or `"REPORT_TOO_LARGE"`. The latter includes `reportBytes` when measured locally. No report is silently truncated, rewritten or partially stored. Upstream ingestion HTTP 413 is also treated as a report-size rejection. No SQL migration is required; this enforces the bound already present in migration 001.

The extension handles 413 before generic JSON parsing, including HTML proxy errors. A rejected frozen snapshot stays visibly failed, and neither automatic retries nor **Retry sync** resubmits it. Export JSON while the scan is available, or rescan after the page changes. Other eligible scans continue uploading. Existing network/backoff/429 recovery remains supported. Sign-out or panel closure still clears the in-memory queue. Existing oversized local records remain readable/exportable; they are not deleted or migrated.

Review verdicts are `open`, `fixed`, `accepted_risk`, and `false_positive`. A verdict records the user's assessment; it does not establish that remediation is complete and does not change the historical evidence, score or hash. Compare against a fresh scan to check changes.

The local SHA-256 check establishes consistency with a stored hash, not third-party attestation. Anyone who can rewrite both the report and stored hash can defeat it. The raw scan route is not an anchor. Optional local anchoring applies separately to frozen insights; see the M5 API section below.

### Pagination and complete totals

Both list endpoints accept integer `page` (1–10,000) and `limit` (1–100, default 50). Responses include `total`, `page`, `limit`, and `scans` or `sites`. An out-of-range page returns an empty array with the real total. Ordering is newest `scannedAt` first, then descending scan UUID to break ties. The site order uses each origin's latest scan. A site with no remaining scans is excluded.

`/api/sites` also returns `overview: { latestHigh, averageScore }`: the high/critical finding count and rounded average heuristic score across **each website's latest scan**, across all pages. An empty workspace returns zero high findings and a null average. `total` counts websites, while each `scanCount` counts all stored scans for that origin. The overview and coverage labels use these global totals; website navigation does not replace the overview's latest-five list. Refresh reloads page one of websites. History's URL filter applies to its loaded page; comparison candidates have their own pagination across all same-URL scans.

Supabase uses `list_scan_page` and `list_site_page` from migration 002. These security-invoker functions retain RLS and take the owner from `auth.uid()`; callers cannot supply another owner. They return one bounded JSON page with counts from the same statement snapshot, so PostgREST's 1,000-row cap no longer truncates history or aggregates. Lists contain summaries, without evidence or review notes; full reports are fetched only for detail/export operations. Local mode has the same response contract but retains its explicit 1,000-scan storage cap.

Pagination is offset based. Inserts/deletes between requests can shift page boundaries; Refresh reloads current data. There is no automatic Supabase retention policy. Exact counts and latest-site metrics still scan owner data; indexes support ordering, but production load/performance at large scale is unmeasured. The page bound limits navigation to `10,000 × limit` results (100,000 in the extension, 300,000 in the dashboard). Cursor pagination and cached aggregates remain future scalability work.

`npm test` includes an in-memory [PGlite PostgreSQL](https://pglite.dev/docs/) regression that applies migrations 001–004, retries 002/003/004, seeds 1,105 scans across 1,103 sites, and checks pagination, counts, deterministic ties, deletion, local-store parity and two-owner/anonymous permissions. Comparison fixtures exercise multiple pages, long URLs, exact matching and target exclusion. It shims Supabase's identity provider; it does not validate hosted Auth, PostgREST or the user's database.

### Saved reviews, comparisons and trends

The dashboard automatically performs numeric ML inference in the browser when saved-scan details opens. The numeric model ships with the app and is managed by VYLNT developers; users do not upload models or prepare training examples. No prediction API endpoint is called and no model, features or predictions are persisted by this API. The bundled model and selected report must have matching ruleset versions; mismatch reports unavailable without changing rule findings. Report JSON, SHA-256, reviews, severity and comparison results are unchanged; ML previews are excluded from exports/Print/PDF. The current release is explicitly synthetic and establishes no real-world accuracy. Training and model-quality evaluation remain developer-owned/offline; see [ML documentation](../ml/README.md).

The earlier user-facing annotation/export form has been removed. Offline `ml:prepare`, `ml:train` and `ml:bundle` commands support developer preparation, training/evaluation and app bundling. Snapshot LSTM support adds `ml:prepare -- --sequence`, `ml:train:lstm` and `ml:demo:lstm`. React validates the numeric release, computes recurrent predictions locally and displays existing versioned rule guidance as recommended changes. The bundled LSTM is synthetic alert triage, with no demonstrated useful security quality. Structural snapshot order does not establish runtime data flow. No background training on user scans, annotation upload or new database write is enabled. Saved feedback is not automatically treated as a training label. This does not implement combined ML report persistence or blockchain anchoring.

Migration `004_comparison_index.sql` (after 003) adds a generated `page_url_hash` column and an owner/hash/time/ID index. The comparison RPC first narrows by the stored lookup key, then requires exact URL equality; hash collisions cannot merge distinct page histories. MD5 is used only for a bounded index key, never for integrity verification. Reports, SHA-256 hashes, RLS, response fields and API routes remain unchanged. Existing deployments on 003 continue to function without this optimization.

The generated column is backfilled and the index built while the migration holds table locks. Schedule an appropriate maintenance window for a populated deployment and test duration in staging; do not assume a zero-downtime migration. The script can be reapplied. Local before/after measurements and limitations are in [PERFORMANCE.md](PERFORMANCE.md); hosted deployment and performance remain unverified.

PDF exports use the same authenticated owner lookup as report detail before launching Chromium. Missing/unowned IDs return 404; malformed IDs return 400. Success is `application/pdf`, attachment `vylnt-<scanId>.pdf`, with `Cache-Control: no-store`. Busy/unavailable renderers return 503 plus `Retry-After: 5`; normal API rate limits also apply. No database migration is required. The PDF contains the original report's SHA-256 and its recomputed match result, not a hash of the PDF. Reviews remain separately labeled mutable decisions. Unsaved drafts/trends/comparisons are excluded.

There are two distinct PDF paths. GET `/api/reports/:id/pdf` returns the full saved finding data, severity/confidence and review notes without generated recommendations or ML. Dashboard **Print / PDF** likewise prints every finding regardless of the onscreen filter. POST `/api/reports/:id/insights/pdf` receives React's `{modelHash, values}`, validates the bounded schema, verifies the current model hash and each result against independently recomputed bundled-model outputs (numeric tolerance 1e-12), then renders trusted results. Ownership is checked before model verification/rendering; unknown/unowned IDs return 404. Invalid payloads return 400, stale/modified analysis 409, and renderer busy/failure 503. Its filename is `vylnt-<scanId>-insights.pdf`.

The insights PDF contains matching issue groups, counts, one recommendation per group, three evidence previews (240 characters; URL previews 180 characters), experimental prediction counts and model identity/provenance. Synthetic results cannot establish useful relevance or justify hiding alerts; rule severity still determines ordering. Ordinary inference stays in React; server recomputation verifies an explicitly requested export. Neither route persists an ML report, changes the original scan/hash, hashes the combined output or performs blockchain anchoring. The existing hash printed in both views identifies the original immutable scan JSON only. Review notes are excluded from insights, retained in raw server PDFs.

Rendering uses [Playwright's PDF API](https://playwright.dev/docs/api/class-page#page-pdf) with an A4 layout, bundled font and tagged output. PDF finalization preserves reading structure, adds language/title/XMP and PDF/UA-1 role mapping, and marks repeated page-number footers as artifacts. Full-data exports start each finding on a new page and retain complete evidence; separate insights exports use natural pagination and bounded previews. One renderer is allowed per process with no queue; startup is capped at ten seconds and rendering at twenty seconds. The isolated context blocks network access and page JavaScript; template values are HTML-escaped. PDFs are held in memory and not persisted. Install Chromium with `npm run setup:browser` and its system dependencies on Linux. The server reads `dist/server/plex-sans.ttf` relative to the project root. Public deployments still need shared gateway limits and CPU/memory/load measurements; the local cap is not distributed enforcement. Three controlled PDFs (insights, full-data and empty) passed veraPDF 1.30.3's automated PDF/UA-1 profile. Prior full-report Edge/Narrator reading and 200% zoom were user-confirmed; the revised split layouts have not received separate native screen-reader acceptance. English and sampled accented European text are accepted; other languages/readers and arbitrary report shapes remain outside this evidence. See [M3 acceptance](M3_ACCEPTANCE.md) for reproduction and retained font-parser warnings.

The extension's **History trends** disclosure reuses `/api/scans/:id/comparisons?page=1&limit=30`, fetching summaries only when opened or refreshed. The selected report is added in memory, then points are sorted chronologically. At most 31 observations are displayed; the selected report may be older than the recent window. Counts disclose truncation. Exact values and coarse collection coverage accompany the discrete plots. Summary responses omit ruleset versions, so pairwise full-report comparison is needed to check those. No new RPC, storage or permission is required. Trends do not alter scores, reviews, hashes or exports.

In the extension, open **Saved scans**, select a report and expand a finding to save a review verdict and up to 1,000 characters of notes. Failed saves retain the draft while that report stays open. Drafts are discarded when switching reports or closing/signing out of the panel. Saved decisions persist separately in the existing feedback table; original findings, score, exported report and hash are unchanged. Concurrent edits use the last saved decision; there is no collaborative merge/conflict UI.

Open **Compare saved scans** on a saved report in either client. The picker loads ten same-URL candidates per page and excludes the selected report; it is independent of the history page. Migration 003 adds `list_comparison_page`, with security-invoker RLS and owner selection from `auth.uid()`. Missing/unowned targets return HTTP 404. Page bounds and ordering match history. Candidate filtering/counting still processes owner data; production-scale query tuning remains open.

Comparison direction is selected report minus chosen baseline. Shared pure code matches stable finding IDs and reports newly observed, no longer observed and changed severity/confidence/evidence. Timestamps alone do not count as changes. It shows score delta and warns when core coverage or ruleset versions differ. Coverage indicators are coarse: equal indicators do not guarantee identical observation completeness. No-longer-observed findings are not automatically marked fixed. Review verdicts do not influence comparisons. Baselines may be older or newer; the chosen timestamp is displayed. Comparison results are temporary and not stored in the database or included in JSON report exports.

## Request limits and recovery

Each API process applies three fixed-window allowances. Requests consume every applicable allowance, including rejected payloads and retries; idempotent uploads still cost authentication/database work.

| Setting | Default | Scope |
| --- | --- | --- |
| `VYLNT_RATE_WINDOW_MS` | `60000` | Window duration in milliseconds; positive integer, at most 3,600,000 |
| `VYLNT_RATE_IP_MAX` | `600` | All `/api` requests from a socket address, before authentication; IPv6 grouped by /64 |
| `VYLNT_RATE_USER_MAX` | `300` | Requests from a verified owner, shared across refreshed tokens |
| `VYLNT_RATE_WRITE_MAX` | `60` | POST/PUT/PATCH/DELETE requests from that owner, before body parsing/storage |

Allowances must be positive integers at most 100,000; zero and malformed values stop startup. Defaults apply in local and Supabase modes. Health/config requests use the address allowance; CORS preflight and dashboard static assets do not. Reading saved scans remains possible after exhausting only the write allowance. Responses expose `Retry-After`, `RateLimit` and `RateLimit-Policy` to allowed browser origins; throttling responses use `Cache-Control: no-store`.

The implementation uses [express-rate-limit](https://express-rate-limit.mintlify.app/reference/configuration). Default local operation keeps HMAC-keyed counters in process memory with a random salt. These expire/reset on process restart and are not shared across replicas. Normal npm/local development requires no Docker or Redis.

Forwarded headers are ignored by default. Optional `VYLNT_TRUSTED_PROXIES` accepts explicit IPs/nonzero CIDRs; only configured peers/chains contribute trusted forwarding information. A future ingress must overwrite caller-provided forwarding headers and restrict direct API access. Review [Express proxy guidance](https://expressjs.com/en/guide/behind-proxies/) before deployment. These controls do not limit direct Supabase Auth/public RPC calls.

Optional `VYLNT_RATE_STORE=redis` enables shared counters through `VYLNT_REDIS_URL`, a 32..512-character `VYLNT_RATE_KEY_SECRET` without whitespace and an optional `VYLNT_RATE_NAMESPACE` (default `vylnt`). All replicas must share the backend, namespace, secret, windows and limits. Separate expiring bucket prefixes prevent client/user/write counters colliding; keys contain HMAC digests, not raw addresses or owner IDs. Prefer `rediss://` for remote connections; protect Redis with authentication and network restrictions. The connection URL/secret are server-only and are not returned by `/api/config`.

Redis startup waits at most five seconds; commands time out after two seconds. Protection failures return HTTP 503, `code: RATE_LIMIT_UNAVAILABLE` and `Retry-After: 5`, without falling back to unshared memory. Automatic reconnect remains bounded per attempt. `NODE_ENV=production` additionally requires Redis mode, Supabase storage and explicit HTTPS allowed origins. The implementation/configuration paths passed local unit tests and builds; actual Redis/multi-process behavior remains unverified. Production deployment is not complete.

Docker implementation and current deployment are excluded at the user's request. No container files/commands or Redis service are required for the current localhost workflow. M2's development scope is complete with the verified live Supabase behavior. Redis, production load and hosted index/plan inspection remain unverified future deployment work and do not block current product development.

The side panel reads HTTP 429 before parsing the body, including HTML proxy responses. It accepts whole-second or HTTP-date `Retry-After` values, uses a 30-second wait for missing/malformed values, and pauses all queued uploads until the deadline. **Retry sync** cannot shorten that wait. The first attempted report stays frozen; successful retry does not include later page changes. Existing exponential backoff and five-attempt limits still apply. A wait exceeding one day pauses the connection's automatic sync until reconnecting later. Closing the panel or signing out still discards its in-memory queue/session.

The dashboard and connection screens show wait guidance on throttling; they do not automatically repeat imports, deletions or review writes. Wait, then repeat the action. No database migration is needed for this increment. Rebuild, restart the API, and reload the extension to activate it.

Validated on 2026-10-16: TypeScript, 62 automated tests, production builds and both Chromium browser suites passed, including a real panel fetch receiving an HTML 429, an eight-second queue cooldown, manual-retry suppression and immutable recovery. The dashboard wait message was also checked. Full results are recorded in `PLAN.md`; live hosted acceptance and multi-instance load testing remain separate.

## Supabase PostgreSQL

1. Create/configure a Supabase project under your account.
2. Apply `supabase/migrations/001_initial.sql` once, followed by `002_pagination.sql` and `003_comparison.sql` from the same folder. Existing installations with 001 already applied should run **002 then 003**; if 002 is already applied, run only 003. The later migrations add read functions/indexes without rewriting reports and can be reapplied safely. Apply them before restarting the updated API. Missing RPCs return actionable HTTP 503 migration guidance.
3. Set `VYLNT_STORAGE=supabase`, `SUPABASE_URL`, and `SUPABASE_PUBLISHABLE_KEY` in `.env`. The `NEXT_PUBLIC_SUPABASE_URL` / `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` aliases and legacy `SUPABASE_ANON_KEY` are also accepted. Secret/service-role keys are rejected at startup.
4. In Supabase **Authentication → URL Configuration**, set the Site URL to `http://127.0.0.1:4318` for local use and add that same URL to allowed Redirect URLs. Add the dev-dashboard origin too if using Vite separately. Keep email confirmation enabled.
5. Run `npm run build` and `npm run dev`. Open the extension side panel, select **Load workspace connection**, choose **Create account**, confirm your email, then return to the panel and **Sign in**. Existing users can sign in directly. Passwords go directly to Supabase Auth over HTTPS, not through the VYLNT API.
6. Grant the displayed API/Supabase host permissions. Select **Rescan page** in the panel; new scans upload automatically while signed in. Use **Saved scans** for history, evidence, JSON downloads, hash verification and deletion. The web dashboard is optional.
7. Sessions refresh automatically while the page is open. `persistSession` and URL-token detection are disabled; closing or reloading the dashboard/extension page discards the local session. Sign-out revokes the current session when Supabase is reachable. No credentials are written to project files or browser storage by the application.
8. Set `VYLNT_ALLOWED_ORIGINS` to exact dashboard origins. Serve production traffic over HTTPS and deploy a reverse proxy with rate limits before exposing the API publicly.

The API verifies each JWT with Supabase Auth. REST requests forward the same JWT; RLS filters reads/deletes/feedback. The ingestion function has a fixed empty search path and obtains the owner only from `auth.uid()`. Direct table writes for scans and findings are revoked; the RPC performs immutable insertion transactionally.

The ingestion RPC is callable by authenticated owners. It is a data-storage boundary, not proof that an observation came from an untampered scanner. The hash and rules do not attest to scan truthfulness. A signed ingestion model would be separate future work.

## CI and automated scanning

```powershell
npm run setup:browser
npm run lab:tls
npm run lab
# In another terminal:
npm run scan:ci -- --url https://127.0.0.1:5443/insecure --ignore-https-errors --output reports/insecure.json --fail-on medium --min-confidence high
```

Exit 0 means policy passed, 1 means qualifying findings exceeded the policy, and 2 means execution/configuration failed. Reports are still written for exit 1. The default gate is high severity and high confidence, so cookie-name heuristics at medium confidence do not fail it by default. Set `--min-confidence medium` only after reviewing that tradeoff.

The runner defaults to loopback targets and blocks non-loopback network resources in that mode. `--allow-remote` is required for other authorized targets. TLS verification bypass is allowed only for localhost test fixtures. Normal remote scans verify TLS.

`.github/workflows/ci.yml` runs type checks, tests, builds, real Chromium regression checks and saves artifacts. It tests that the controlled insecure HTTPS fixture fails the configured gate while the hardened fixture passes. The workflow is present locally; it has not been run on GitHub. Require its check in branch protection if you want failed checks to block merges.

# Saved insights reports

- `POST /api/scans/:id/insight-reports` with `{ "analysisHash": "<SHA-256 of canonical browser analysis>" }`: authenticated finalisation. The API independently rebuilds all assessments/templates from the saved scan. Returns 201 for new content, 200 for an existing version, 409 for stale analysis and 413 above 1 MiB.
- `GET /api/scans/:id/insight-reports`: owner-scoped saved-version identities and creation times.
- `GET /api/insight-reports/:sha256.json` (or no extension): retrieves and verifies the frozen envelope/content.
- `GET /api/insight-reports/:sha256.pdf`: renders that frozen version. Model/policy mismatch or tampering returns 409; a renderer failure returns 503 and Retry-After.
- `GET /api/reports/:id/pdf` is unchanged: complete findings/severity/evidence without generated actions or ML.
- Legacy `POST /api/reports/:id/insights/pdf` returns 410 for the owner, with update guidance. Synthetic fixture parsing remains available only in developer code/tests.

Supabase requires migration `005_insight_reports.sql`. Reports are immutable and deleted alongside their source scan. The user JWT enforces ownership; no service-role key is used. RPC storage alone is not an attestation of API origin: retrieval checks canonical integrity and trusted derivation as well. Combined and original scan hashes are separate. Optional local anchoring uses the combined digest only; hashes alone do not establish an anchor.

## Local blockchain proof API (M5)

With `VYLNT_BLOCKCHAIN=local` and local deployment configuration, successful finalisation automatically queues the saved version's digest. The frozen response shape stays unchanged. A journal failure returns the saved report with `X-VYLNT-Anchor-Warning`; repeated finalisation retries enqueue. The journal/chain are independent of local/Supabase content storage; no migration 006 or user tokens in the journal.

React calls finalisation automatically when generated analysis completes; no download action is required. It displays the returned combined SHA-256, adds/reuses the frozen version and leaves blockchain confirmation to the separate status/verification controls. Analysis errors/incompatibility cannot bypass server validation; aborted navigation may leave a successfully committed immutable version but cannot update the new scan's UI. Reopening the same content is idempotent.

| Method | Owner-scoped route | Result |
|---|---|---|
| GET | `/api/insight-reports/:id/anchor` | `{ enabled, proof?, warning? }`; recorded status is not live verification |
| POST | `/api/insight-reports/:id/anchor/retry` | Empty JSON `{}` only; requeue a failed job or missing current-instance job; disabled returns 503 |
| GET | `/api/insight-reports/:id/verify` | `{ result, message, proof? }`; matching, not-anchored or verification-unavailable |
| GET | `/api/insight-reports/:id/anchor-proof.json` | Separate attachment containing recorded proof; 404 if no job exists |

All four routes require a verified owner-scoped frozen report and valid original-scan linkage. Missing/cross-owner reports return 404; changed content/source returns 409 with `result: content-mismatch`. Arbitrary client digests are rejected. Proof v1 contains reportHash, chainId, contractAddress, instanceId, queued/submitted/confirmed/failed status, attempts, optional transactionHash/blockNumber/blockHash/error. No raw signed transaction, signer, owner identifier or scan contents are exposed. Verification always queries the live local chain and checks deployment/bytecode/writer, successful receipt, event, canonical block and registry lookup. Downloading a proof is not itself successful live verification. Original `/api/reports/:id/verify` remains a local raw-scan hash check with `anchored:false`.

See [local setup and limits](M5_ACCEPTANCE.md). Frozen report JSON and PDF stay unchanged, including their historical hash explanations; the separate proof carries on-chain metadata. Public attestation, replica/cross-machine synchronization and permanent chain persistence are outside M5.

## Delete a saved website group

`DELETE /api/sites?origin=https%3A%2F%2Fexample.test` removes the authenticated owner's saved scans for an exact HTTP(S) origin and returns `{ "deletedScans": number }`. Origins with paths, credentials, query strings, fragments or extra query parameters are rejected (400). Other owners' rows are excluded by the local owner namespace or forwarded user-JWT RLS; anonymous requests return 401. Missing groups return zero, so retrying is safe.

The API gathers owner-scoped scan IDs using keyset pagination and deletes the captured IDs in batches of 100, cancelling unsent anchor jobs first. Findings, notes and frozen insights cascade with each source scan. A failure may leave a partially removed group; the dashboard refreshes and explicitly offers retry. Concurrent newly uploaded scans can recreate the website. Already submitted blockchain transactions remain. Website lists derive from remaining scans; an empty Supabase `sites` bookkeeping row can remain under the existing RLS grants. No new migration/privileges or hosted verification is claimed. Individual scan deletion remains `DELETE /api/scans/:id`.
