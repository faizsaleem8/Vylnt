Do not silently re-evaluate earlier v3/version-2 candidate artifacts under this new policy. Legacy v2 reviewed policy is preserved; v3 is not a production release format.

The corpus now has ten pinned MIT applications / 90 files. `ml:applications -- --application <exact-id> --profiles <comma-separated-profile-ids>` selects explicit isolated checks; empty/unknown selections fail. Each source requires a real application smoke test. Label only controlledTargetIndexes matches, not unrelated original findings. See [expansion](ML_CORPUS_EXPANSION.md). The accepted 170 scenarios and frozen once-only model evaluation are complete; do not rerun or optimise against the consumed test. Exact numeric publications contain no private reports/labels. New quality experiments require preregistered data/candidates and honest controlled scope.

The separate developer-only evidence-v3 experiment is documented in [ML_EVIDENCE_V3.md](ML_EVIDENCE_V3.md). Select it explicitly with `ml:prepare:insights -- --schema vynlt-evidence-v3`, then `ml:insights:v3`. Use `ml:verify:candidate` to execute hash-bound browser numeric parity without consuming a test. Unknown legacy CSP collection coverage stays unknown. Current v3 coverage is insufficient for qualification; v2 release commands reject v3 rather than silently promoting it.

Current scope (2026-10-22): the user removed independent human review from this experimental phase. Use controlled specifications and automated oracles; paired-review commands and reviewed-release steps below are optional/legacy, not prerequisites. A trained controlled candidate is now bundled through a separate display-only policy. The original reviewed release command remains unchanged and must not be bypassed with fake reviews. No category passed quality qualification; the user does not need to prepare data or recruit reviewers. Further distinguishable data and broader held-out evaluation remain developer-owned quality work.

Ordinary users only scan and download reports. They never annotate, upload a model, train or configure an AI provider. Private reports/review records live under ignored `.local/`, `ml/data/` or another private developer directory. Only bounded numeric weights and a public scope/qualification manifest may be bundled.

The approved pinned open-source corpus is documented in [ML_APPLICATION_CORPUS.md](ML_APPLICATION_CORPUS.md). Run `npm run ml:applications:fetch` explicitly for verified source download, then `npm run ml:applications` offline after TLS/browser setup. It runs 2048, TodoMVC and reveal.js under VYNLT-controlled local configurations, retains their licences and creates exclusive private scans/oracle records/controlled review packets. Those are three source families before numeric grouping, not independently reviewed application examples. Prepare and audit a completed run's manifest using steps 2–3 below. No application install/build scripts are executed.

1. Run `npm run ml:controlled` after `npm run lab:tls` and `npm run setup:browser`. It writes an exclusive directory under `.local/ml-controlled/runs/` (optional `--output <new-private-run>`), preserving old snapshots. This starts only ephemeral loopback HTTP/HTTPS servers. Network/header/HTML/resource assertions use Node clients independently of VYNLT detection rules; the new persistent-preference case also verifies browser readability and expiry. Generated template variants remain one actual family.
2. Run `npm run ml:prepare:insights -- --manifest <completed-run>/manifest.json --output <completed-run>/dataset.json` with a private, stable `VYNLT_ML_DATASET_KEY` of at least 32 characters. Keep the key outside Git. To combine runs, retain each source snapshot and use one private manifest whose reportFile paths resolve to those snapshots, with original family/label/provenance/oracle fields intact. The output contains only numeric features, category/severity/coverage, labels, provenance and opaque hashes. No URLs, cookie names, raw code or review prose enter the dataset.
3. Audit before fitting: `npm run ml:insights -- audit --dataset <dataset.json> --output <new-split-audit.json>`, then `npm run ml:insights -- readiness --dataset <dataset.json> --output <new-readiness.json>`. Outputs are exclusive. All variants from a shared application/template belong to one actual family. Equivalent model inputs join family components so they cannot cross partitions. Readiness reports missing classes/families without fitting a model. Expand genuine application coverage when partitions are insufficient; keep the frozen assignment policy. Preparation uses immutable output names and keeps datasets under ignored private directories or an explicit external private location.
4. Train a new candidate directory: `npm run ml:insights -- train --dataset <dataset.json> --output <new-candidate-directory>`. Input hash and split freeze before fitting. Training and validation require both classes after conflict/coverage filtering. Only development (training/validation) conflicts may populate the model's abstention list. The complete label audit may identify held-out conflicts for reporting; held-out labels cannot create runtime safeguards. The LSTM has eight hidden units, at most 74 steps and a maximum 128 KiB artifact. The logistic comparator uses the same full tensor/length and partitions. Preprocessing fits training only; validation selects checkpoint, temperature and thresholds. The 0/1 threshold pair explicitly disables classification, including floating-point saturation. A refused experiment leaves a failure record.
5. Evaluate once: `npm run ml:insights -- evaluate --dataset <same-dataset.json> --output <candidate-directory>`. `candidate.json` binds the exact model, comparator, parity and training files before evaluation. Changed weights, thresholds, calibration or comparator are rejected. An exclusive consumed marker prevents reusing this candidate's test for threshold searches. Evaluation publishes per-category metrics/intervals and model-only/guarded comparisons, including contextual decisions on insufficient-evidence targets. Guards use observable uncertainty, original severity and development conflicts only. They cannot inspect test labels. Evaluation-policy revision 2 and its candidate/evaluation hashes are required by the release command; older evaluations are not releasable. Within-family correlation limits interpretation of Wilson intervals.
6. Perform independent application review using the private workflow below. Human-reviewed targets require two distinct review declarations with date, scope and independent evidence references. Agreement produces one target label; disagreement produces one needs-review example. Original private decisions remain auditable. Review counts do not inflate training counts. Controlled fixtures retain controlled provenance even when people review them. Preparation checks declarations structurally; it cannot attest reviewer identity or independence.
7. Create a private release review JSON: version 1, independentApplicationReview true, datasetHash, evaluationHash (SHA-256 of evaluation file bytes), public scope, approvedCategories and optional name. A category needs every gate in `ML_BUILD_PLAN.md`; controlled-only data cannot approve relevance de-emphasis.
8. Run `npm run ml:release:insights -- --model <candidate-directory/model.json> --evaluation <evaluation.json> --review <private-review.json> --output <new-release.json>`. Keep candidate.json and its bound files together. This rejects controlled/synthetic provenance, stale identity, invalid metric units/intervals and failed gates. The shared runtime/staging gates use qualification policy `vynlt-reviewed-release-v2`. Only explicit `--bundle` changes the shipped release; previous model identities are archived. Update PLAN.md, retain versioned policy/catalog implementations and run relevant regression before release.

Candidate numerical parity is checked against exported PyTorch scores with absolute tolerance 1e-6. Legacy v1 parsers/fixtures remain for development. The shipped v2 controlled model uses the experimental path below and cannot determine relevance or hide findings; evidence-summary fallback remains available on incompatibility.

## Controlled experimental release (current track)

After steps 1–5, run:

```powershell
npm run ml:release:experimental -- --candidate <frozen-candidate-directory> --dataset <same-private-dataset.json> --output <new-private-release.json> --bundle
npm run check
npm run test:ml-report -- --report <completed-app-run>/reveal-unpinned-script.scan.json
```

The command requires controlled provenance, matching dataset/split identities, an exclusive test-consumption marker, the bound candidate/evaluation files and real Python/browser parity for every supported category. It stages a versioned `display-only` release even if classification qualification fails; it always records zero qualified categories. It does not relabel controlled examples as reviewed or change the original reviewed gate. Published evaluation failures remain visible. Only non-conflicting eligible development variants receive supplemental signals; unknown evidence requires review. Frozen decimal signals are rounded to four places, and the integration test compares the built browser Worker hash with API finalisation/idempotency/retrieval after reload. The test adds 71 repeated script references only for acceptance, never training.

Experimental scores cannot change assessments, severity, actions or contextual placement. Release metadata changes are archived even when weights stay the same, and historical frozen content must match one complete trusted release derivation. Model identity, candidate/evaluation hashes, scope and policy are frozen with the report. Rebuild/restart the API and reload clients after bundling. These checks establish a functioning experiment; M6's count/family/quality qualification remains unmet. See `ml/evaluations/README.md` for the actual first experiment.

The initial controlled fixture intentionally assigns different application intents to equivalent observable metadata. Those conflicts demonstrate an information limit: a recurrent network cannot recover context that was never collected. Additional distinguishable evidence and representative frozen holdouts are required before useful qualified category predictions; the current experimental policy does not make them.

## Collection coverage and correlated uncertainty

Run `npm run ml:insights -- collection-plan --dataset <private-dataset.json> --output <new-private-brief.json>` before collecting another cohort. This immutable diagnostic reports actual family/input components, eligible development classes, unknown evidence, conflicting variants and remaining reviewed-test counts for each of the eight categories. Controlled examples never reduce reviewed-application acceptance deficits. It does not rename families, change splits, assign labels or select model parameters. Equivalent inputs link application families transitively; adding pages or renamed fixtures may leave one component. Keep private briefs alongside the dataset, outside shipped sources.

Evaluation retains Wilson intervals and adds deterministic paired application-family bootstrap intervals for LSTM, logistic and rule-only results, both before and after safeguards. Whole families are resampled with the same draw across models (seed 42, 1,000 repetitions). LSTM-minus-comparator intervals describe paired precision/recall/coverage differences. Fewer than two families or more than 5% undefined denominators yield a null interval with defined-replicate counts. These exploratory intervals do not establish independence of related families, modify release gates or tune thresholds. They describe only the evaluated cohort.

Candidate parity cases now cover available development category/class length extremes, at most 32 cases, without using test examples. Release staging executes those hash-bound cases through the browser numeric implementation before writing a release, requires every approved category and absolute error <=1e-6, and rejects enlarged tolerances or malformed structural sequences. The committed synthetic boundary fixture is separately reproducible with `python -B ml/export_boundary_parity.py`: all eight categories at 2, 26, 50 and 74 steps. It proves numeric mechanics only, not security quality; its cases are never training data or application reviews.

## Private review commands

This workflow is for VYNLT developers and independent reviewers. It adds no user-facing training controls. A packet contains sanitized snapshot metadata and grouped facts, with no suggested model labels or rule recommendations. Its hash binds source, family and source kind. Use an actual application/template family identifier; generated variants of one template stay together.

```powershell
npm run ml:review -- create --report <authorised-saved-scan.json> --family <application-family> --source-kind application --output .local/reviews/app.packet.json
npm run ml:review -- status --packet .local/reviews/app.packet.json
npm run ml:review -- record --packet .local/reviews/app.packet.json --decision .local/reviews/independent-decision.json
npm run ml:review -- export --packets .local/reviews/packet-paths.json --output .local/reviews/paired-manifest.json
```

`packet-paths.json` is an explicit array of packet paths relative to that file. Omit `--source-kind application` for controlled fixtures; the default is controlled and those packets cannot be exported as reviewed application data. No automatic sign-off or fabricated reviewers are provided.

Each independent decision requires packetHash, caseId, reviewerId, reviewedAt (ISO timestamp), scope, one of the three labels and `independentEvidence` containing recordId, the actual evidence record's SHA-256 and independentOfVynltRules=true. Verify application behaviour/configuration independently of VYNLT rules. Keep evidence records and attribution private. Do not copy cookie values, credentials, request bodies, page text or raw code into packets or training annotations.

The record command accepts one decision per reviewer/case, journals it and uses an exclusive packet lock. Changed evidence requires a new packet/review. Export requires two distinct reviewer declarations per case; private decisions remain available for agreement auditing. Preparation collapses duplicate review annotations, records disagreement rates and rejects conflicting family assignments for a scan. This does not prove the declared reviewers are different people; that remains an independent developer audit obligation.
